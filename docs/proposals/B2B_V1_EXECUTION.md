# B2B v1 execution plan

**Status:** Product and engineering plan, 2026-09-27. Proposed product behavior; it does not amend `spec/canonical.json`.

## Customer and workflow

The first customer is an organization that wants to make consequential choices consistently with its stated mission and retain evidence of who decided what. The v1 workflow is **Mission Workspace**:

1. A verified person creates an organization workspace and becomes its owner.
2. The owner completes the seven-question Mission Contract as an organization draft, with a measurable outcome and affected people.
3. The owner invites a reviewer to that workspace.
4. An authorized member proposes one operating decision using the Mission Decision Compiler's human, organization, beneficiary, mission, exposure, externality, evidence, and reversal lenses.
5. A different authorized member reviews a fixed revision, records a reason, and approves or rejects it.
6. Members can read a chronological audit history and export the contract, decision, review, and evidence references.

This is a commercial **Mishys** workflow applying the open Missionism protocol. It should remain technically separable from this public protocol site. Neither a submitted contract nor an approved operating decision certifies a Mission, issues Mission Units, forms a legal entity, or changes the canonical protocol.

**Why this slice:** It delivers an institutional memory and decision process to an existing organization without first solving securities, incorporation, physical operations, or network liquidity. It exercises the durable tenancy, identity, authorization, versioning, and audit foundations that Sparks, pilots, Team-Ups, and events will later need.

## Data and trust boundaries

- Production storage: managed PostgreSQL with reviewed migrations, encrypted backups, restore drills, and separate environments. Local development/tests may use a PostgreSQL-compatible embedded database; its local files are not production storage.
- Identity: managed sign-in with verified email, secure server session, revocation, and organization membership checked on every read and write. The existing Firebase hosting direction makes Firebase Authentication a candidate, subject to project setup and an end-to-end session test.
- Authorization: owner manages membership; editor proposes and revises decisions; reviewer approves or rejects a fixed revision. An actor cannot review their own proposal. Server enforces roles and tenant scope; UI visibility is convenience only.
- Audit: append-only organization event records written in the same transaction as each state change. Each event has actor, tenant, object, action, timestamp, schema version, and before/after revision references. No silent update of submitted content. Correction means a new revision or reversing disposition with a reason.
- Evidence: references and metadata first. Do not store raw transcripts, salaries, or private participant records in this v1 flow.
- Public protocol claims remain sourced from `spec/canonical.json`. Workspace policies are product rules, labeled as such.

## Milestones and acceptance

### M0 — Audit and scope (complete)

The workflow, prototype gaps, and release gates are recorded here. Existing files and local records remain intact.

### M1 — Durable data foundation (in progress)

Versioned PostgreSQL schema and repeatable migrations for users, organizations, memberships, contract revisions, decisions, reviews, and append-only audit events. Tenant-linked foreign keys prevent cross-organization references. Tests cover constraints, migration replay, rollback of a failed state change, and persistence across restart. Production connection must fail closed when configuration is absent.

**Implemented locally:** versioned schema migrations, checksum/replay logic, tenant constraints, immutable history triggers, transactional services, and a PostgreSQL adapter that fails closed without `DATABASE_URL`. PGlite tests cover constraints and restart persistence. A local PostgreSQL 18 check database ran `workspace:migrate` and a complete `workspace:pg-smoke` workflow. A `pg_dump` custom-format backup was restored into a separate check database; `workspace:restore-check` compared migration history and every row in every workspace table. Managed staging database and provider backup recovery remain open.

### M2 — Identity and membership

A new user can register/sign in, create one workspace, invite a verified reviewer, revoke access, and sign out. Server rejects anonymous, expired, revoked, and cross-tenant requests. Session, CSRF, rate limiting, and invite expiry have tests. Browser journey uses two distinct accounts.

**Implemented locally:** the server-side role policy denies cross-tenant and revoked membership, limits actions by role, and looks up a submitted decision revision before allowing an independent reviewer. Firebase Authentication sign-up, verified-email server sessions, CSRF protection, sign-out, and organization creation were exercised in the local emulator and browser. An owner can issue a seven-day, single-use, email-bound invitation link, revoke it, or revoke a member; acceptance and revocation each write an audit event in the same transaction. At most 25 live links may be pending in one organization. PostgreSQL-backed per-account quotas now cover verified session exchanges, successful organization creation, and successful invitation creation across app instances. Browser checks used two verified accounts to accept a reviewer invitation, read the submitted contract without edit controls, then lose list and direct-page access after revocation. The browser also displayed the organization creation quota error after five successful creations. Provider-level abuse controls, live project configuration, and staging session tests remain open.

### M3 — Mission Contract

Owner can save, submit, and read a seven-question contract with measurable mission, beneficiaries, harms, evidence, and value-sharing statements. Submitted revisions remain readable. Validation and concurrency failures have useful errors. A second tenant cannot read or modify it.

**Implemented locally:** owner form and authenticated API save partial drafts and require all seven answers on submission. Each save creates an immutable revision with a matching audit event in the same transaction. Browser verification covered partial draft save, clear incomplete-submission error, completed submission, history, and persistence after reload. A separate signed-in account received a 404 for that contract's organization page. Integration tests cover validation, stale revision, editor and cross-tenant denial, rollback, and immutable history.

### M4 — Decision and review

Editor can draft and submit a decision record tied to a contract revision. Reviewer sees the exact submitted revision and approves or rejects with a reason. Self-review and stale-revision review are denied. The decision record is legible in one page and its status is derived from committed events.

**Implemented locally:** operating decision drafts and submitted revisions are bound to a submitted Mission Contract. Submission requires the fifteen Decision Compiler lenses; the form records evidence links without fetching or judging them. An independent owner or reviewer can approve or reject the latest submitted revision with a reason. A new review records the reviewer’s assessment of all seven hard gates; approval requires all marked clear, while an unresolved or triggered gate requires a note and can only accompany rejection. The reviewer cannot edit, and the proposer cannot review their own revision. Integration tests cover missing lenses, missing/unresolved gates, draft review denial, stale revision, self-review, duplicate review, tenant scope, rollback, and immutable reviews. Browser verification covered both an approved pre-gate review and a new rejected review with an unresolved safety gate; attempting approval with that gate produced a clear error without a review. Historical reviews remain labeled as legacy and unassessed instead of receiving fabricated clearances. This provisional product rule still needs founder review for customer wording and authority before launch; the software does not certify legality, safety, or Mission status.

The decision page now displays the exact submitted Mission Contract revision selected when the decision was created, alongside the decision being reviewed. Its expandable history shows the content and review for each decision revision. A test confirms that a later Mission Contract edit leaves the decision bound to its original revision.

### M5 — Audit and export

Every consequential transition appears in the organization audit view. Export includes schema version and stable IDs for independent inspection. Tests prove no missing or extra event after successful or failed transactions. A backup and restore drill reproduces the same records.

**Implemented locally:** member-only audit view and versioned JSON export with organization, memberships, invitations (without bearer token hashes), all revisions and reviews, audit events, and a SHA-256 checksum. Export uses a repeatable-read, read-only PostgreSQL snapshot. Organization-local event sequence numbers now give new events a durable order; older events are clearly marked as estimated-order backfills. A read-only audit checker detects missing, duplicate, extra, and mismatched core workflow events. Service tests compare event counts and reject cross-tenant or revoked readers. The browser displayed the full local workflow's 11 events and requested the export with HTTP 200. Local PostgreSQL backup and restore reproduced all table rows. Managed backup/restore and customer retention policy remain open.

An offline `workspace:verify-export` command now checks a downloaded file's checksum, schema version, ordered events, event-to-record pairings, and core cross-record links without contacting the service. It is an integrity and consistency check, not a digital signature or a substitute for the database audit checker.

### M6 — Release gate

Production database, secrets, migration job, backup schedule, error monitoring, health checks, and recovery runbook are configured and exercised in a staging environment. Build, lint, typecheck, unit/integration tests, security and cross-tenant tests, browser journeys, and staging smoke tests pass. A real customer trial still requires an explicit launch decision.

**Implemented locally:** `/api/workspace/health` checks authentication project configuration, database availability, and migration history; `docs/WORKSPACE_OPERATIONS.md` records release, smoke, backup, restore, and incident procedures. Unexpected workspace API, health, and server-rendered page failures emit a redacted structured log with a request ID; customer-facing errors display that reference. Expired or revoked Firebase credentials remain authentication failures, while unexpected identity-service errors surface as service failures instead of masquerading as bad credentials. A built browser runtime showed a matching UI/log reference during a deliberately unavailable local database, recovered against the healthy one, and retained a 404 for a missing organization. Managed staging, actual alert delivery, provider backups, live Firebase, and a staging browser journey remain release blockers.

An explicit one-time PostgreSQL environment binding now connects a release runtime to a staging or production database and its Firebase project. The binding command checks the actual database name and records the selected Firebase project; the runtime rejects a different target or identity project, and an unmarked production workspace runtime fails closed. These controls have only local synthetic evidence; they do not replace managed staging setup.

The draft [v1 pull request](https://github.com/bryan-benchmark/missionism/pull/1) now has a passing GitHub `Workspace checks` run. CI verifies Node 22 installation, repository tests, lint, dependency audit, a staging-marked build with synthetic Firebase settings, restricted PostgreSQL permissions and workflow, a logical restore, and audit integrity. It does not exercise live Firebase, provider backups, alerts, or a managed staging browser journey.

## Open founder decisions

1. **First customer segment:** recommend a 5–50 person organization with a real mission and recurring operating decisions. This determines the exact templates, onboarding language, and pilot recruitment.
2. **Commercial product identity:** recommend **Mishys Workspace** for the SaaS, while Missionism remains the open protocol. This determines domain and deployment boundaries.
3. **Decision authority:** v1 uses organization-local owner/editor/reviewer roles. Constitutional or reserved-matter approvals require a separately reviewed governance design; this workflow must not imply they are handled.
4. **Recovery targets:** recommend one-hour recovery point and four-hour recovery time for the first paid pilot, subject to managed service capability and cost. These are not yet an SLA.
5. **Decision hard gates:** the provisional v1 product rule now requires a reviewer assessment of all seven gates and blocks approval while any are unresolved or triggered. Recommend keeping that rule, while founder and legal counsel approve customer wording and decide when specialist signoff is required. A clear assessment is a human statement, not evidence that the software verified legality or safety.

Independent engineering work can proceed while these are reviewed.

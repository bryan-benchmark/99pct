# Mission Workspace operations

**Status:** staging runbook draft, 2026-09-27. The local workflow works with the Firebase Auth emulator and PostgreSQL/PGlite; no managed staging or production workspace has been configured. This document describes the release and recovery work that remains. It does not change the canonical Missionism protocol.

## Environments and secrets

- Use separate Firebase projects, App Hosting backends, and PostgreSQL databases for staging and production. Never point a preview or local emulator at customer data. Set the staging backend's App Hosting **Environment name** to `staging` so Firebase merges `apphosting.staging.yaml` with the base config. Keep the existing public protocol backend on the base config; do not change its environment name merely to test the workspace. [Firebase environment configuration](https://firebase.google.com/docs/app-hosting/multiple-environments).
- Runtime configuration: `DATABASE_URL`, `FIREBASE_PROJECT_ID` (or provider supplied `GOOGLE_CLOUD_PROJECT`), `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, and `NEXT_PUBLIC_FIREBASE_API_KEY`. Use `FIREBASE_SERVICE_ACCOUNT_JSON` only if the runtime does not supply appropriate application credentials. Store database credentials and any service account JSON in a secret manager, not in Git or a public build variable. Set `WORKSPACE_MIGRATION_DATABASE_URL` for the migration job when using a separate migration role; do not expose it to the app runtime. [Firebase App Hosting configuration](https://firebase.google.com/docs/app-hosting/configure).
- Set the two `NEXT_PUBLIC_FIREBASE_*` values on the staging backend before building; these identify the browser's Firebase web app and are compiled into the client. Keep them available at runtime too: Next evaluates its configuration on startup and the workspace checks the runtime project. `apphosting.staging.yaml` sets `WORKSPACE_RELEASE_TARGET=staging` for **BUILD and RUNTIME** and references the `missionismWorkspaceStagingDatabaseUrl` secret for **RUNTIME** only. Create that secret and grant the staging backend access before rollout. With the marker, Next fails its build if browser Firebase settings are missing or demo values, server/browser project IDs conflict, or an emulator/development store is configured. The base public-site build remains available without workspace identity settings. The marker is a build gate, not proof that the live Firebase service works; the two-account staging browser journey is still required. Console environment values take precedence over YAML, so inspect the effective rollout variables. [Firebase configuration and precedence](https://firebase.google.com/docs/app-hosting/configure).
- Do not set `FIREBASE_AUTH_EMULATOR_HOST`, `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_URL`, `WORKSPACE_DEV_DB_DIR`, or `WORKSPACE_LOCAL_TEST_RUNTIME` outside local development. The production database adapter fails closed without `DATABASE_URL`. A built local Next server may omit `WORKSPACE_RELEASE_TARGET` only with `WORKSPACE_LOCAL_TEST_RUNTIME=1`, loopback Firebase server and browser emulator settings, matching `demo-` project IDs, and a loopback PostgreSQL database whose name ends in `_check`. An emulator setting alone never exempts a production-mode runtime from the release target requirement. Staging and production reject the local-test flag.
- Workspace page responses, including invitation and sign-in redirects, send `Referrer-Policy: no-referrer` so token-bearing URLs are not sent as referrers when a visitor follows a link. Dynamic workspace pages also return `Cache-Control: private, no-cache, no-store`; verify both headers through the deployed edge before release.
- Restrict the database role used by the app to the workspace database. Create distinct runtime and migration credentials; give the runtime role only the grants in `scripts/workspace-runtime-grants.sql`. It can append history but cannot update or delete history or alter schema. Run `npm run workspace:check-runtime-role` with the runtime `DATABASE_URL` before deploying. Use the migration credential for rate-limit pruning via `WORKSPACE_MAINTENANCE_DATABASE_URL`; the runtime role has no `DELETE` grant. Configure TLS and network restrictions in the managed database; verify the actual connection in staging.

## Release sequence

1. Verify staging secrets and a current managed backup. Record the backup identifier and restore point outside this repository.
2. Require the `Workspace checks` pull-request workflow to pass, then run `npm ci`, `npm run verify`, `npm run lint`, `npm run build`, and `npm audit --audit-level=moderate` with Node 22 against the release commit. CI uses a disposable PostgreSQL service, a restricted role, synthetic Firebase build settings, and a logical restore; it is not managed staging evidence. For a workspace release, set `WORKSPACE_RELEASE_TARGET=staging` with the real browser Firebase values during the build; a missing value must stop the build. Review the migration SQL before rollout.
3. Run `WORKSPACE_MIGRATION_DATABASE_URL=<staging migration connection> npm run workspace:migrate` as a separate job before deploying the new app. The migration runner checks names and SHA-256 hashes, rejects missing or reordered history, and applies each new file transactionally. It also accepts `DATABASE_URL` for local development. Migration `0006_environment_binding.sql` creates an initially unbound environment record; `0007_environment_identity.sql` adds the Firebase project binding. After confirming the actual database name and intended Firebase project, run `WORKSPACE_RELEASE_TARGET=staging WORKSPACE_EXPECTED_DATABASE_NAME=<actual-staging-db-name> WORKSPACE_EXPECTED_FIREBASE_PROJECT_ID=<actual-staging-firebase-project-id> WORKSPACE_MIGRATION_DATABASE_URL=<staging migration connection> npm run workspace:bind-environment`. The command rejects a different database name and refuses to relabel an already bound database or Firebase project. An older target-only binding must be explicitly claimed with its intended Firebase project before the new runtime starts. Then run the grants file as the schema owner using `psql -v ON_ERROR_STOP=1 -v app_role=<existing-runtime-role> -f scripts/workspace-runtime-grants.sql`; run `DATABASE_URL=<staging runtime connection> npm run workspace:check-runtime-role`. Repeat grants and the role check after migrations that add tables or change privilege needs. A production database must be bound separately to `production` and its own Firebase project using its actual name and migration credential.
4. Deploy the app. Require `GET /api/workspace/health` to return `200 {"status":"ready"}`. A release runtime fails closed if its browser/server Firebase project IDs differ, its database environment or Firebase project binding differs from the runtime, or its migration history differs from the packaged SQL. This does **not** prove the external Firebase service is reachable or that backup recovery works.
5. Run the browser journey with two verified staging accounts: create organization, submit contract, invite reviewer, submit decision, review, inspect audit, download export. Check 401/403/404 paths and event counts. Run `DATABASE_URL=<staging runtime connection> npm run workspace:check-audit` after the journey; it must report no issues. Use synthetic staging data only.
6. Watch 5xx rate, sign-in/session failures, database connection errors, migration failures, and backup status after rollout. App rollback alone does not reverse a database migration; prefer additive, backward compatible migrations.

Unexpected workspace API failures return HTTP 503 with an `X-Request-ID` header and a customer-visible reference. Server-rendered workspace pages show the same kind of support reference on unexpected failures. Search structured server logs for the matching `requestId`; records include a fixed operation name and a safe PostgreSQL SQLSTATE when available. Logs intentionally omit request bodies, customer email, tokens, SQL parameters, connection strings, and exception messages. Health failures return the same header. Expected business denials such as 404 and 409 are not incident logs. Before release, connect these JSON logs and health status to a managed dashboard and alert route. Starting alert candidates are sustained workspace 503s for five minutes, any failed migration or daily rate-limit pruning job, and a missed managed backup; tune thresholds against staging traffic and test alert delivery.

Session exchanges are limited to 30 per verified account per UTC hour, organization creation to 5 per account per UTC day, and invitations to 30 per owner account per UTC day. PostgreSQL enforces these quotas across app instances; HTTP 429 tells the customer when to retry. They do not replace provider-level protection against anonymous credential guessing or abuse of account creation. Schedule `WORKSPACE_MAINTENANCE_DATABASE_URL=<maintenance connection> npm run workspace:prune-rate-limits` daily to remove expired quota windows, and alert if it fails. The maintenance credential needs `DELETE` on `workspace_rate_limits`; the migration credential is one option, subject to the provider's policy. The table is operational state and is included in database backups, but it is not part of the customer audit export.

The app pool limits each SQL statement to 10 seconds and abandons a transaction left idle for 15 seconds; new connections wait at most five seconds. A PostgreSQL timeout becomes a traceable workspace service failure, so investigate the matching request ID and slow query before increasing limits. The migration job uses a five-minute statement timeout and a six-minute idle transaction timeout. Size the managed database for up to ten app connections per instance at the configured maximum of ten instances, plus jobs and administration; lower the pool or instance cap if the service cannot support that budget.

Member-scoped multi-statement reads use short read-only repeatable-read transactions. Authorization and returned rows share one snapshot; a revocation committed after that snapshot does not change the in-flight response, while the next request must see revoked access. Watch connection use and slow reads in staging, since each such read occupies one pool connection until the snapshot closes.

Migration `0005_audit_sequence.sql` gives each organization's new audit events a durable, contiguous sequence assigned under its organization row lock. Preexisting events are numbered by stored timestamp and ID; their `sequence_backfilled` flag warns that exact historical commit order cannot be reconstructed. Export schema version 2 includes both fields, and the audit page displays the sequence. The read-only `workspace:check-audit` command verifies sequence continuity and one matching event for each organization creation, contract revision, decision revision, review, invitation creation/revocation, and accepted invitation. It compares selected source fields in those events and replays membership and invitation transitions to compare their final roles and statuses with stored rows. It cannot establish exact commit order for backfilled events or serve as cryptographic proof against a privileged database operator. Run it after migration, after restore, and on a regular operations schedule; investigate any mismatch before relying on an export. Each organization is checked in a repeatable-read snapshot, so repeat a check after a period of concurrent writes if needed.

After downloading a customer JSON export, run `npm run workspace:verify-export -- <downloaded-export.json>` from this repository. This offline command checks the schema version, SHA-256 checksum, event sequence and core event-to-record pairings, member and decision links, and independent reviewer identity. It prints only the organization ID and counts. A mismatch returns a nonzero exit code. Keep the downloaded file in access-controlled storage under the customer's retention policy: it contains member emails and decision records. The checksum detects changes to that file but does not prove who created it, and this command does not replace the database audit checker or a backup.

## PostgreSQL smoke and restore drill

The smoke command requires a **dedicated disposable database** whose name ends in `workspace_check`. It writes synthetic `example.test` records and leaves them there for inspection. Never pass a production database URL.

```bash
WORKSPACE_TEST_DATABASE_URL=<dedicated-check-db-url> npm run workspace:pg-smoke
```

For the runtime privilege drill, migrate the dedicated check database with its schema owner, apply the grants file to an existing restricted test role, and run:

```bash
DATABASE_URL=<restricted-check-db-url> npm run workspace:check-runtime-role
WORKSPACE_TEST_DATABASE_URL=<restricted-check-db-url> WORKSPACE_TEST_MIGRATION_DATABASE_URL=<check-db-schema-owner-url> npm run workspace:pg-smoke
```

The smoke test then runs the full customer workflow through the restricted role. Confirm direct `UPDATE audit_events`, `DELETE decision_reviews`, and schema creation attempts are refused by PostgreSQL. These are checks on the actual deployed role, not only on application permission code.

For a logical backup drill, use PostgreSQL client tools compatible with the server. The commands below assume a dedicated check database and a separate empty restore database; supply credentials through the approved secret mechanism. Store the dump in encrypted, access-controlled storage and remove local copies under the organization's retention policy. Custom format dumps are restored with `pg_restore`. [PostgreSQL dump documentation](https://www.postgresql.org/docs/current/app-pgdump.html), [restore documentation](https://www.postgresql.org/docs/current/app-pgrestore.html).

```bash
pg_dump -Fc -f <backup-path> <dedicated-check-db-url>
createdb <empty-restore-db-name>
pg_restore --no-owner --no-acl --exit-on-error -d <restore-db-url> <backup-path>
WORKSPACE_TEST_DATABASE_URL=<dedicated-check-db-url> WORKSPACE_RESTORE_DATABASE_URL=<restore-db-url> npm run workspace:restore-check
```

The restore checker requires both database names to end in `_check` and confirms that the connections resolve to distinct database names, even if their URLs differ. It verifies migration checksums and compares every row of every workspace table, including invitation token hashes, audit events, and rate-limit windows. It also confirms that update attempts on immutable history are rejected and that an audit insert receives the next sequence number. The insert probe is rolled back and checked absent afterward. The checker requires a synthetic workflow with contract, decision, and review rows before backup. The customer JSON export is useful for inspection but is **not** a database backup and its checksum is **not** a signature. A managed point-in-time restore drill and documented recovery time remain required before release.
Run `DATABASE_URL=<restore-db-url> npm run workspace:check-audit` on the restored database too. A row-for-row match and an audit pairing check answer different recovery questions.

## Incident recovery

1. Identify whether the incident is app logic, identity, database availability, corruption, or unauthorized access. Preserve logs and the latest backup identifier.
   Ask for the customer-visible reference ID and correlate it with the structured server log. Do not ask customers to send session cookies, invitation links, or credentials.
2. For possible data corruption or unauthorized writes, stop workspace writes by disabling the backend or routing traffic away. Do not attempt to edit append-only revision or audit rows in place.
3. Restore to a new isolated database at the selected recovery point. Run migration and restore checks, then inspect one known organization’s contract, decision, review, membership, and audit export. Compare event counts with preincident evidence when available.
4. Rotate affected database and service credentials. If identity compromise is suspected, revoke affected Firebase sessions and review membership changes. Resume traffic only after a two-account smoke test and health check pass.
5. Record missing data between the recovery point and incident cutoff, customer impact, and any corrective event as a new audited action. Do not silently replay unverified writes.

## Release blockers and owner decisions

- Managed staging PostgreSQL, restricted-role grants, encrypted backups, point-in-time recovery, restore drill, monitoring alerts, and live Firebase configuration are unverified. Local PostgreSQL tests do not close these blockers.
- The database environment binding has been exercised only against a disposable local restore. Before staging, confirm the App Hosting backend's environment-specific YAML is selected, the `WORKSPACE_RELEASE_TARGET` value survives to runtime, and the bound database is the intended managed staging database. A restore of production data into staging retains its `production` label and will fail closed; investigate and use a deliberate, reviewed recovery procedure rather than editing the label in place.
- Recommend a target recovery point of **one hour** and recovery time of **four hours** for the first paid pilot, subject to managed service capability and cost. The founder must accept or change these targets before a customer SLA is offered.
- Email invitation links are manually shared by the owner. Recommend adding managed delivery or SSO onboarding before broader enterprise rollout; link acceptance is still bound to the verified invited email.
- Product and legal review must decide how to describe the Decision Compiler hard gates. Current UI records human analysis and independent review; it does not certify safety, legality, governance authority, or Mission status.
- Reviews created before migration `0004_review_gates.sql` remain visibly unassessed. Do not backfill clearance or treat those historical approvals as gate-checked; create a new decision revision and independent review if an organization needs that assessment.
